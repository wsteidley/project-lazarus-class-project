# Project Lazarus — Data Organization & `build-metric-data` Spec (v1)

Goal: make the metric data **auditable and reproducible** — raw inputs committed and
immutable, derived files regenerated by a committed script, provenance in a manifest.
Someone should be able to delete every derived file, run one command, and get a clean
`git diff`.

This is partly a **check/reorganize** task (some structure exists) and partly a
**build** task (the extractor step is new).

## Decisions (locked)

- **Cited anchors → `data/curated/cited_anchors.csv`** (one CSV, keyed by provider via
  `source_name`), passed through by a thin extractor. Not hard-coded in TS (a data fix
  must not be a code change); not per-provider files (sprawl for 1–3 rows each).
- **Rename `data/input/` → `data/curated/`.** It's the de-facto curated dir (7 CSVs via
  `inputFile()`); `input` misleads about authorship. `git mv` + reference updates in one
  atomic commit.
- **`build-metric-data` stops at `data/derived/`.** It does **not** touch `build-db`.
  The DB schema switch (basis column, capacity_series table, Wright fit) stays in
  `hero-thresholds-spec-v3.1.md`, sequenced after. Nothing in `src/` reads the derived
  files today, so producing them first strands nothing.
- **`.xlsb` extractor → Python/uv**, reusing the `resolve-fuzzy.ts` → `uv run` +
  `##SKIP##` pattern. Not SheetJS (large dep for one occasional file).
- **uv-absent contract (fail loud by default; skipping requires an explicit flag):**
  - **Default, uv absent → hard fail, non-zero, always** (whether or not the file
    exists). Skipping a uv extractor is never implicit. Message names problem +
    consequence + both fixes: e.g. `✗ uv not found — cannot regenerate
    capacity_series.csv (IRENA wind extractor requires uv). Install uv
    (https://docs.astral.sh/uv/), or re-run with --allow-stale-metric-data to use the
    existing committed file.`
  - **`--allow-stale-metric-data`, uv absent → warn + proceed** using the committed
    file if present. The *only* tolerant path, and it's opt-in — running on stale data
    is a deliberate, visible choice.
  - **Flag set but file also missing → still fail.** Nothing to fall back to; a partial
    write is the corruption we're preventing.
  - **uv present → run normally** (flag irrelevant).
  - Principle: *uv-absent is an error you must explicitly override, and the override
    still cannot produce a corrupt file.* This also makes the audit loop correct for
    free — the audit runs with no flag, so uv-absent fails loudly instead of silently
    producing a phantom deletion.
  - Flag is named for **what you accept** (stale data), not what you disable, so it
    isn't reached for reflexively. Document in `README.md`: the audit loop requires uv.
- **Commit `data/derived/**`.** The `rm -rf derived && rebuild && git diff` audit is
  meaningless if untracked. Add a `derived/README.md` banner: "generated — do not edit."

```
    owid/                     # RENAME from our-world-in-data (or keep name; be consistent)

      installed-solar-pv-capacity.csv

    bnef/          .gitkeep    # paywalled → cited-only, no file

    startup-failures/          # EXISTS — company/outcome subsystem

  curated/                    # HUMAN-authored inputs, edited in PRs (RENAMED from data/input/)
    dependencies.csv

  derived/                    # GENERATED by build-metric-data. Reproducible.
    metric_observations_full.csv

  DATA_SOURCES.md             # provenance manifest (already written)
```

Rules to enforce:
- **`sources/` is never edited by code** — read-only inputs.
- **`derived/` is never hand-edited** — add a generated-file banner comment where the
  format allows, or a sibling `derived/README.md` saying "regenerate, don't edit."
- **`curated/` vs `sources/`:** if a human authors/maintains it, it's `curated`; if a
  provider produced it, it's `sources`. (Thresholds are curated; OWID CSVs are sources.)
- Two source *subsystems* share `sources/` but feed different pipelines — tag which in
  the manifest, don't split the folder: `owid/irena/bnef/lbnl/worldbank` → metric data;
  `crunchbase/startup-failures` → company/outcome.

## Part 2 — `build-metric-data` step (new, reproducible)

A step that reads `data/sources/**` + `data/curated/**` and writes `data/derived/**`.
One **provider extractor per source**, each small and self-contained.

```
src/steps/build-metric-data.ts        # orchestrates: run extractors -> assemble -> write derived
src/lib/extractors/
  owid-solar-cost.ts                  # solar-pv-prices.csv     -> observation rows
  owid-solar-capacity.ts              # installed-solar-*.csv    -> capacity rows (AC)
  irena-capacity.ts                   # IRENA .xlsb              -> onshore wind + PV capacity
  bnef-battery.ts                     # hard-coded cited anchors (no file)
  ...
```

Requirements:
- **Each extractor declares its output basis** and stamps `source_url` + `source_name`
  per row, matching `DATA_SOURCES.md`.
- **Report-not-drop:** an unparseable/unknown row is reported in the build summary,
  never silently dropped (same discipline as the rest of the pipeline).
- **Deterministic:** same inputs → byte-identical outputs (stable sort, fixed rounding),
  so `git diff` after a rebuild is the audit.
- **`.xlsb` reading:** needs an xlsb reader. If done in TS, use a lib that reads xlsb;
  if easier in the existing Python (uv) side, make it a Python extractor invoked the
  same way as the Splink step. **Encode the IRENA gotcha:** capacity is on
  `Producer Type ∈ {On-grid electricity, Off-grid electricity}`; `"All types"` rows
  have null capacity (finance only) — sum on/off-grid, exclude "All types".
- **Idempotent + standalone:** runnable on its own (`npm run build-metric-data`) and as
  a pipeline stage **before `build-db`**.

## Part 3 — Wire into the pipeline

- Add `build-metric-data` to the orchestrator graph, upstream of `build` (the DB build
  consumes `data/derived/**`).
- It depends only on `sources/` + `curated/` — no LLM, no network — so it's cheap and
  always safe to re-run.

## Audit / update / extend (the payoff)

- **Audit:** `rm -rf data/derived && npm run build-metric-data && git diff` → empty diff
  proves the committed derived files reproduce from raw sources.
- **Update:** replace a file in `data/sources/<provider>/`, re-run, review the diff.
- **Add a source:** new `sources/<provider>/` dir + new extractor + manifest row —
  no existing extractor touched.
